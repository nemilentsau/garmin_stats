Why this needed a system

The problem was never whether an assistant could compute charts. The problem was whether it could avoid producing a clean, confident, wrong health story.

Wearable data is noisy, missing in structural ways, autocorrelated, and often device-derived from overlapping raw signals. Garmin stress and HRV, for example, can look like two independent signals while still sharing heart-rate-derived origins. A fast assistant can easily overfit that material unless the analysis process makes failure modes explicit.

Failure mode

Good-looking charts can be bad evidence

Gaps can become fake trends, wide scans can surface chance hits, and summary averages can hide distribution shape.

System response

Different risks need different rulebooks

The project uses multiple skills because parser correctness, statistical discipline, evidence discipline, presentation, and tests are different jobs.

The high-level skill system

These six skills sit at the same conceptual level. Each protects one category of mistake that could invalidate the analysis or distort how it is read.

garmin-data

Raw Garmin correctness

Protects FIT parsing, field names, units, SDK quirks, and UTC-to-local timestamp handling.

data-analysis

Statistical discipline

Protects missingness handling, spread, effect sizes, chart choice, and visual inspection.

finding-analyst

Evidence discipline

Protects questions, run contracts, templates, recipes, confidence tiers, and promotion rules.

analytical-dashboard

Truth-preserving display

Protects information hierarchy, chart selection, density, and number formatting.

ux-design

Interface comprehension

Protects spacing, wording, interaction patterns, and visual emphasis from implying false certainty.

testing

Regression protection

Protects parser, backend, workflow, and frontend behavior when code changes.

Skill drill-downs

Each subtab explains one skill. finding-analyst is one peer skill here; its templates and recipes are nested inside that skill, not presented as top-level method concepts.

garmin-data

This skill owns the raw Garmin boundary. It tells the analyst which FIT files exist, which message schemas are trusted, which fields are already parsed, and which timestamp or filtering rules must be obeyed before any daily metric can be trusted.

Use whenTouching FIT parsing, adding a Garmin metric, debugging nulls, or checking SDK drift.
Ownsfit_parser/, schema references, parser facade, field names, scale factors.
PreventsWrong message fields, wrong units, UTC/local mistakes, and invalid readings.
OutputClean health contracts and daily metrics safe enough for analysis.

What a cold reader needs to know

Source shape Garmin archives arrive as data/garmin_health_stats/YYYY-MM-DD.zip, extract into dated folders, and contain multiple FIT files per day.
Parsed files WELLNESS, SLEEP_DATA, HRV_STATUS, and SKIN_TEMP are parsed. METRICS, SLEEP_DISRUPTIONS, and rare NAP files are acknowledged but not fully parsed.
Timestamp rule FIT timestamps are shifted to local time per reading, using a UtcOffsetTimeline built from each file's own offset markers (day-wide union as fallback). New timestamp fields are not display-safe until they go through that path.
Schema discipline Known message types live in references/*.json. The analyst trusts those first, runs verification when data drifts, and discovers fields only when a metric is missing from the schemas.

Rules that directly affect findings

Metric areaRuleWhy it matters for analysis
Heart rateMonitoring HR has no usable full timestamp; group by parent day.A time-of-day claim from the wrong timestamp would be false.
WellnessRead all 5-7 WELLNESS files for the day.A partial day can fake lower stress, HR, SpO2, or respiration.
HRVHRV values use Garmin scaling and zero means no reading.Wrong scale or zero handling changes effect sizes.
StressUse stress_level_time; discard negative stress values.Invalid "unknown/calculating" samples cannot be treated as physiology.
Respiration and SpO2Discard negative respiration codes and zero SpO2 readings.Device status codes are not biological readings.

data-analysis

This skill owns statistical and chart discipline after Garmin data is parsed. It is the reason a finding must report spread, missingness, sample size, visual inspection, and effect size instead of only a clean average or a compelling chart.

Use whenComputing aggregates, building charts, inspecting metric behavior, or evaluating a claim.
OwnsDaily/period stats, distribution checks, chart choice, spot checks, traces.
PreventsMean-only claims, hidden missingness, misleading axes, and uninspected plots.
OutputEvidence that a reviewer can audit without trusting a screenshot.

Two layers it governs

LayerWhat it controlsReader-visible consequence
AggregationMean, median, q1, q3, min, max, null handling, period summaries from raw readings.Findings show the distribution, not just one center value.
PresentationChart type, axis integrity, IQR bands, smoothing disclosure, gap handling, spot checks.Charts answer a question and do not imply unobserved trends.

Required analysis habits

Never mean aloneEvery reported center needs sample size and spread; skewed metrics prefer median and IQR.
Missingness is dataNull rates and gap clustering are recorded because sensor dropout is often not random.
Use librariesUse numpy and scipy for statistics; do not hand-roll percentiles or correlations.
Plot before trustingGenerate and inspect evidence images. A plot must have title, units, date range, and smoothing window if any.
Spot-check valuesValidate at least 2-3 plotted values against source data before the chart becomes evidence.
Ask "so what?"If a chart does not support a decision or interpretation, redesign it or remove it.

finding-analyst

This skill owns the investigation workflow. It does not parse Garmin files and it does not replace statistical discipline. It defines how a question becomes a durable run folder, how templates create the evidence trail, how recipes name the methods, and when a local run is allowed to affect FINDINGS.md.

Use whenInvestigating a Garmin question, scout signal, anomaly, lag, or proposed finding.
OwnsRun types, run folders, templates, recipes, confidence, gates, promotion.
PreventsGoalpost moving, fluke promotion, unverifiable chat-only claims.
OutputA reviewed finding or a documented no-signal run.

Templates: what every run must record

Templates are not methods. They are audit forms copied into a run folder so a reviewer can see what was asked, what data was used, what evidence exists, and what promotion is proposed.

01-question.mdLocks the question before results can move it.
  • Records run type, question-led mode, one concrete question, date window, metrics, context sources, and exclusions.
  • For quoted numbers, requires a reported-number check against the snapshot before analysis.
  • For surface/display questions, flags whether API or frontend tracing is needed.
  • For hypothesis tests, stores prediction, decision rule, and pre-registered comparisons.
  • For exploratory/scout runs, declares recipes, breadth, ranking rule, and mid-run recipe additions.
02-data-profile.mdProves the data slice is known before the claim is read.
  • Records data source, snapshot timestamp, snapshot file, row count, and date boundaries.
  • Requires per-metric present days, missing days, missing percent, and gap clustering.
  • Captures null-vs-zero handling, impossible/capped values, sensor/parser caveats, and filters.
05-findings.mdSeparates claim, evidence, method, interpretation, caveats, and confidence.
  • Each finding must state the claim in one sentence.
  • Evidence must include effect size, spread, sample size, and chart references.
  • Method names recipes from RECIPES.md, not ad hoc phrasing.
  • Caveats must include alternatives, confounders, missingness, and multiple-comparison posture.
  • Confidence is set here: tentative, provisional, or confident.
  • No-signal runs record what was tested and why it did not clear noise.
06-review.mdForces downgrade-only review before promotion.
  • Walks six gates: question, data, statistical, visual, interpretation, findings.
  • Records a verdict for each plot: supports, weakens, or complicates.
  • Records confidence changes as was -> now with the reason.
  • Review can downgrade confidence; it cannot upgrade it.
07-findings-update.mdMakes the permanent record patch mechanical.
  • Contains the exact proposed FINDINGS.md addition or diff.
  • Moves resolved, parked, or invalidated questions with back-references.
  • Retracts invalidated takeaways with a dated note rather than deleting history.
  • Records snapshot-section corrections when numbers drift after a snapshot bump.

Recipes: methods and the traps they guard against

Recipes are named analytical techniques. Declaring a recipe tells the reviewer what method was used and what failure mode should be checked.

RecipeStatusQuestion shapeTrap it guards against
Anomaly windowvalidatedWhich windows deviate across metrics?Outlier-heavy means and correlated metrics inflating a "simultaneous" event.
Pairwise correlation sweepvalidatedWhich metric pairs co-move?Obvious within-cluster correlations swamping truly under-documented pairs.
Change-pointvalidatedWhen did a metric baseline shift?Missingness or one outlier day masquerading as a regime change.
Lagged correlationvalidatedDoes A on day D predict B on day D+k?Calendar gaps, autocorrelation, and multi-lag false positives.
Partial-correlation controlvalidatedDoes A-B survive an obvious control C?Shared derivation or common-cause structure being mistaken for an independent signal.
Period comparisonvalidatedWhat separates two windows by effect size?Circularly choosing windows by the outcome and then testing them as if independent.
Missingness patternvalidatedWhen does a metric drop out?Treating structured sensor dropout as random absence.
Distribution shapevalidatedIs a metric skewed, bimodal, or regime-mixed?Calling a pooled regime mixture an intrinsic distribution shape.
Loading-stability comparisonvalidatedIs a multi-metric axis stable across windows?Range restriction or missing overlap being read as structural change.
Normalization window sweepvalidatedWhich baseline should normalize a score?Choosing a baseline by hindsight without coverage and sensitivity checks.
Day-type clusteringvalidatedAre there real recovery-day archetypes?Clustering a one-dimensional continuum and naming the bins as states.
Trigger searchcandidateWithin a bad window, what moved first?Overreading threshold-sensitive first-deviation dates.
Single-point contextcandidateIs one sharp move anomalous?Promoting a single non-replicable point without coverage context.
Rule/threshold bake-offcandidateWhich classifier or threshold display is least bad?Comparing bucket cuts while ignoring flicker from discretization itself.
Weekday / cyclic seasonality bootstrapcandidateDoes a calendar-cycle pattern survive de-trending?Autocorrelation manufacturing a weekday effect under iid tests.

Quality gates

QuestionConcrete question, date range, metrics, type, and pre-registration when needed.
DataSnapshot pinned, coverage measured, nulls/zeros/impossibles and filters documented.
StatisticalSample size and spread, effect size before p-values, baseline and comparison count stated.
VisualEvery evidence plot inspected, units/ranges sane, gaps not bridged, values spot-checked.
InterpretationClear "so what", alternatives named, exploratory labeled, no medical advice.
FindingsConfidence tier and promotion target match the evidence and caveats.

Confidence and promotion

tentativeSingle recipe, no replication, or many-comparison hit. Stays in the run folder.
provisionalMultiple recipes converge or a pre-registered rule passes, but a real ceiling remains. Promotes only as an attributed observation with caveat.
confidentProvisional-grade evidence clears every quality gate and survives review. Promotes as an analytical takeaway.

analytical-dashboard

This skill owns truth-preserving presentation. It decides how evidence should be shown once the analysis exists: chart type, density, hierarchy, labels, units, and the visual anti-patterns that can make a weak claim look strong.

Use whenChoosing charts, arranging findings, formatting numbers, or judging dashboard density.
OwnsInformation hierarchy, chart selection, axis integrity, data density, formatting.
PreventsDecorative charts, misleading scale, false hierarchy, and unreadable density.
OutputA presentation where the visual strength matches the evidence strength.

Rules used on findings pages

Question -> chartTrend uses line chart, distribution uses histogram/box plot, relationship uses scatter, comparison uses bar or aligned table.
No visual exaggerationBar axes start at zero; line axes may narrow but must disclose the baseline and avoid flattening meaningful variation.
Direct labelsPrefer labels, units, and titles near the data over legends that force eye-jumping.
No anti-patternsNo pie charts, 3D, rainbow scales, dual-axis manipulation, or vanity metrics.
Health conventionsSleep, HRV, stress, SpO2, respiration, and temperature each carry conventional units and visual expectations.

ux-design

This skill owns interface comprehension. It keeps the method page from becoming a decorative artifact dump, and it keeps dashboard UI from implying certainty, priority, or computation ownership that the evidence does not support.

Use whenChanging page layout, spacing, typography, controls, visual polish, or dashboard surfaces.
OwnsReadable desktop layout, interaction controls, copy hierarchy, visual emphasis.
PreventsMarketing layout, card clutter, text squeeze, and UI that hides the analytical question.
OutputA screen that can be scanned by a cold reader without misreading the claim.

Project-specific UX rules

Operational clarityThis is a dense Garmin health app, not a landing page. Use compact headings, restrained color, and predictable controls.
Display-only frontendThe UI must not compute statistics, smoothing, exposure logic, or derived values. It shows backend/API results.
Cards lastUse cards for independent entities. If items need comparison, use tables or aligned rows so the reader can scan across them.
Stable dimensionsToolbars, tabs, charts, and counters should not shift when content changes.
Desktop validationFrontend changes require npm run check and browser screenshots at the normal desktop viewport.

testing

This skill owns regression protection. It tells the project when tests are needed, what classes of behavior must be covered, and which tests are false comfort because they only assert implementation details.

Use whenWriting or reviewing tests, especially parser, ingest, watcher, startup, or backend behavior.
OwnsBranch coverage, boundary cases, failure modes, equivalence classes.
PreventsHappy-path-only coverage, duplicate examples, brittle mock/prompt assertions.
OutputTests that would actually catch the regression the change can introduce.

Decision framework

BranchesEvery if, elif, else, and early return creates a required behavior case.
BoundariesEvery comparison such as >=, <=, >, or < earns tests at and around the limit.
Failure modesError paths matter as much as the successful path.
Equivalence classesOne test per branch and boundary class; delete duplicate examples that cover the same behavior.
Do not testLLM output text, prompt strings, or that a mock was called. Test outcomes, side effects, and errors.

Filesystem/startup behavior must prove no-op safety

StateRequired proofReason
Missing outputWork runs when extracted files or derived state do not exist.Fresh installs must build state.
Already in syncA second run with unchanged inputs does no work.Startup/watchers must be idempotent.
Stale outputChanged source input refreshes or replaces derived output.Data drift must not leave stale state.
Error pathInvalid archives or missing dirs do not corrupt state.Failure must be contained.

One real run: stress to HRV

This example is a finding-analyst case file. It shows what the analyst run actually recorded, which recipes it declared, which gates reviewed the claim, and why the result was promoted as provisional rather than confident.

2026-05-26-stress-hrv-lag

The run asked whether an acutely high-stress day predicts suppressed nightly HRV over the next 1-3 nights, beyond the known same-night stress-HRV relationship. The answer was yes for lag +1, with a fast decay by lag +2/+3, but the claim stayed predictive and provisional because Garmin stress and Garmin HRV share HRV-derived measurement inputs.

Before dataOnly one predictor/outcome pair was allowed: stress on day D -> HRV on later nights.
Allowed lagsOnly D+1, D+2, and D+3 could be tested; lag 0 was reference context, not a discovery.
Snapshot357 days, 2025-06-01 to 2026-05-26, frozen at 2026-05-26T20:00Z.
Metricsstress_avg(D) predictor; hrv_nightly_avg(D+k) outcome.
Success ruleD+1 had to clear r <= -0.20, then survive same-night stress control.
Final tierprovisional predictive, not causal.

What 01-question.md locked before analysis

Contract fieldWhat was writtenWhy it mattered
Question Does stress on day D predict lower HRV on D+1, D+2, or D+3 beyond same-night coupling? The run cannot drift into a broad stress/HRV story after seeing results.
Prediction Inverse association, strongest at lag +1, decaying by lag +3. The expected shape is known before the plot exists.
Primary rule Forward signal only if lag +1 Spearman r <= -0.20 with n >= 100. A visible negative chart is not enough; it must clear a numeric threshold.
Decisive rule Partial Spearman of stress(D) vs HRV(D+1), controlling stress(D+1), must keep |r| >= 0.10 with CI excluding 0. This distinguishes a forward predictor from same-night stress-HRV coupling plus autocorrelation.
Comparison count Exactly three forward lags: +1, +2, +3. Lag 0 is reference only. The many-comparison posture is explicit; weak lag +2/+3 results cannot be promoted later.
Exclusions No causal mechanism claim, no other metric pairs, no raw FIT re-parsing, no manual logs. The finding stays scoped to one predictive mart-level relationship.

What the template files forced this run to make explicit

The file names are not the explanation. The useful content is the specific decision each file forced before the result could be promoted.

FileSpecific commitment in this runWrong move it prevented
01-question.md Before looking at results, the run committed to one pair: stress_avg(D) predicting hrv_nightly_avg(D+1..D+3). No other metric pairs, no extra lags, no causal mechanism claim, and no manual logs were allowed. Turning a single lag result into a broad stress/HRV story after seeing the chart.
01-question.md The run wrote the pass/fail rule up front: lag +1 had to reach Spearman r <= -0.20 with n >= 100, then the stricter partial check had to keep |r| >= 0.10 with a CI excluding 0. Calling any negative-looking lag curve a result without a pre-written threshold.
02-data-profile.md The run froze 357 daily rows and recorded the missingness that affects this question: stress had no missing days; HRV had 13 missing days, including a Nov 5-20 cluster. Letting the reader assume the lag test used a complete daily series.
02-data-profile.md The run recorded the exact sample sizes after pairing real calendar dates: lag 0 n=344, lag +1 n=342, lag +2 n=340, lag +3 n=338. Missing HRV nights were dropped, not bridged. Creating fake lag pairs by jumping across missing nights.
03-analysis.py The script paired stress(D) with HRV(D+k) only when both exact calendar dates existed and both values were present. Example from the profile: 2025-11-17 stress was not paired to a later available HRV value when 2025-11-18 HRV was null. A "lag +1" result that secretly spans more than one day.
03-analysis.py The script used rank correlation because stress and HRV are bounded/skewed, then used 7-day moving-block bootstrap because stress(D) and stress(D+1) correlated +0.379. Overstating certainty by treating serially related days as independent observations.
05-findings.md The finding had to state the actual result: lag +1 r=-0.490, partial given same-night stress r=-0.344, lag +2/+3 not claimed, and median next-night HRV 64 ms after low-stress days vs 43 ms after high-stress days. Promoting the headline without the limits and non-results attached.
06-review.md The review passed the gates but still refused to call the result confident because Garmin derives both daytime stress and nightly HRV partly from heart-rate variability. Confusing a passed statistical test with proof of an independent causal channel.
07-findings-update.md The proposed permanent record had to carry the caveat and add an open question about whether the lag is physiological carry-over or shared Garmin derivation. Leaving the caveat behind when the result moved into FINDINGS.md.

Recipes used, and what each guarded against

RecipeHow it appeared in the runTrap it guarded against
Lagged correlation Spearman correlations for lags 0, +1, +2, +3 with effect size, CI, n, and p-value last. Reading a same-night association as a next-night predictor.
Missingness pattern HRV nulls were dropped, never bridged; day D paired with D+k only when both calendar dates existed exactly k days apart. A fake "lag +1" pair spanning a data gap.
Partial-correlation control Decisive rule controlled stress(D+1); robustness also controlled HRV(D), leaving r about -0.34. A lag effect that is only same-night stress coupling or HRV persistence.
Moving-block bootstrap Block length 7, 5000 resamples, because stress autocorrelation was +0.379 and HRV autocorrelation was +0.150. Overstated precision from pretending daily observations are independent.

Why the finding did not become confident

The registered test passed, the decisive partial survived, and every review gate cleared. Confidence still stayed provisional because Garmin derives both daytime stress and nightly HRV partly from heart-rate variability. The result is useful for forecasting, but it is not evidence that stress and HRV are two independent causal channels.
