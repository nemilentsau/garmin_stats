Garmin analysis method page hierarchy

A simple structure document for explaining the project skill setup, where finding-analyst is one high-level skill, and templates/recipes are internal artifacts of that skill.

Reader path

Problem first, system second, skill peers third, drill-downs fourth, one run last.

1. What we are trying to achieve

The method page must explain how this project prevents AI-assisted Garmin analysis from becoming confident storytelling. The cold reader should leave understanding the system of skills, the role of each skill, and how a finding earns its way into FINDINGS.md or the HTML findings pages.

Core thesis: this is not a showcase of templates, recipes, charts, or one impressive run. It is an explanation of a skill-governed analysis system.

Reader need

Understand why the system exists

Wearable data is noisy, missing, autocorrelated, device-derived, and easy to overinterpret. The danger is not calculation failure. The danger is clean, confident, unsupported claims.

Presentation need

Keep findings standalone

The findings pages should still carry their own value. The method page explains provenance and guardrails; it should not bury findings inside implementation detail.

2. Hierarchy rules

01

Start with the failure mode

Before naming skills, explain why unguarded assistant analysis fails on wearable data.

02

Present high-level skills as peers

garmin-data, data-analysis, finding-analyst, analytical-dashboard, ux-design, and testing are the same conceptual level.

03

Drill down after the peer layer

Each skill can have its own subtab. A reader should never see templates or recipes before knowing they are inside the finding-analyst skill.

04

Put templates and recipes under finding-analyst

Templates answer what every analyst run must record. Recipes answer which analysis method a run used. Both are instruments of finding-analyst.

05

End with one real run

The stress to HRV example should demonstrate the hierarchy in motion, not introduce the hierarchy for the first time.

4. High-level skills as peers

This is the core correction. finding-analyst is not a section above the other skills. It is one skill in the high-level system.

garmin-data

Raw data correctness

Prevents parse, unit, Garmin field, FIT-file, and local timestamp errors.

data-analysis

Statistical and chart discipline

Prevents mean-only summaries, hidden missingness, bad chart choices, and uninspected visuals.

finding-analyst

Evidence discipline

Prevents vague questions, goalpost moving, fluke promotion, and chat-only findings.

analytical-dashboard

Truth-preserving display

Prevents chart and dashboard presentation from overstating certainty.

ux-design

Interface comprehension

Prevents layouts, wording, colors, and interaction patterns from obscuring the analytical question.

testing

Regression protection

Prevents code changes from silently breaking parser, backend, workflow, or UI behavior.

5. finding-analyst drill-down

Only after the peer skill layer should the page drill into finding-analyst. This skill owns the investigation workflow. Templates and recipes belong here.

finding-analyst / Overview
What this skill owns: question-led runs, exploratory runs, scout runs, confidence tiers, review gates, promotion policy.
finding-analyst / Run contracts
Question-led, exploratory, and scout runs each have different obligations before data is opened.
finding-analyst / Templates
Templates answer: what must every run record so it can be audited?
01-question.md - scope, question, reported-number check, prediction or recipe declaration.
02-data-profile.md - frozen source, coverage, missingness, null/zero policy.
05-findings.md - claim, evidence, method, caveats, confidence, promotion recommendation.
06-review.md - gates; can downgrade but not upgrade confidence.
07-findings-update.md - exact proposed permanent-record patch.
finding-analyst / Recipes
Recipes answer: what method did this run use, and what trap does that method guard against?
finding-analyst / Promotion
Confidence controls where the output can go: run folder, attributed observation, or asserted finding.

6. One real run

The run example should come after the system has been introduced. Its job is to prove the hierarchy, not to carry the hierarchy.

01

Question fixed before data

finding-analyst uses 01-question.md to lock the stress to HRV question, date window, prediction, and decision rule.

02

Garmin data made analyzable

garmin-data and backend ingestion protect units, timestamps, parser semantics, and persisted daily metrics.

03

Snapshot and coverage checked

finding-analyst uses 02-data-profile.md; analysis does not proceed as if missingness is invisible.

04

Recipes applied

Lagged correlation, partial control, and missing-data pairing are declared as recipes inside the analyst run.

05

Chart and evidence reviewed

data-analysis, analytical-dashboard, and ux-design protect interpretation and presentation.

06

Finding promoted with caveat

06-review.md and 07-findings-update.md determine whether the claim can leave the run folder and how it must be caveated.

7. Scaffold wireframe

This is a proposed page skeleton. It is deliberately plain so the hierarchy can be reviewed before visual design.

Header: Method behind Garmin findings. Short statement of failure mode and system purpose.
Section 1 - Why this needs a system: Noise, missingness, autocorrelation, multiple comparisons, assistant overconfidence.
Section 2 - Skill system overview: Six high-level skills as peer tabs/cards, grouped by failure type.
Section 3 - Skill drill-downs: One subtab per skill. finding-analyst is one of these subtabs.
garmin-data - raw data and timestamp correctness.
data-analysis - statistics and chart discipline.
finding-analyst - investigation workflow. Nested subtabs: overview, run types, templates, recipes, review, promotion.
analytical-dashboard - truth-preserving dashboard presentation.
ux-design - visual hierarchy and usability.
testing - regression protection.
Section 4 - One real run: Stress to HRV run mapped step by step to the skill system and analyst artifacts.
Section 5 - Promotion rule: What gets into FINDINGS.md, HTML findings, or product decisions.
